## Récupération du superviseur — 2026-10-12

Le lanceur local `preproduction/control.py start` sérialise récupération et démarrage avec un verrou OS `filelock` (dépendance déjà déclarée par le moteur). `recover_owner.py` exige une preuve de décès du PID de l'API, arrête seulement les conteneurs attribués aux workspaces configurés, puis retire le verrou propriétaire et ses verrous Node JSON. Les verrous Python, les preuves fournisseur et les états métier ne sont pas supprimés. PID actif ou indéterminable, verrou étranger, lien filesystem et restauration en cours bloquent la reprise. Un PID réutilisé est conservativement considéré actif.

Les fichiers `control.py`, `recover_owner.py`, `watchdog.py`, `boot_watchdog.py` et `install_boot_task.py` doivent être copiés ensemble dans le harness local ; cette archive reste non autonome. Le watchdog externe relance le lanceur après décès des services. Un arrêt explicite pose `supervisor.pause` ; un démarrage explicite réussi reprend la surveillance. Il ne tue pas un propriétaire vivant et ne relance aucune opération métier. Les opérations interrompues restent `execution_unknown` et les travaux en attente exigent une authentification fraîche.

### Démarrage Windows

Depuis le Python déclaré du déploiement, dans un terminal élevé du **même utilisateur**, exécuter `install_boot_task.py DEPLOYMENT_ROOT`. La procédure exige un déploiement local avec fournisseur simulé et ses scripts déjà présents, ainsi que Docker Desktop AutoStart explicitement activé dans `settings-store.json`. Elle refuse une valeur désactivée, absente ou contradictoire, avec prise en compte des variantes `AutoStart`/`autoStart`. Une entrée dans les programmes de démarrage seule ne suffit pas. Elle enregistre les chemins Python/Node/Docker dans `boot-runtime.json`, puis crée `Codex-Voice-Calibration-Watchdog` : déclencheurs au boot et à la connexion de l'utilisateur, principal S4U sans mot de passe stocké, privilèges ordinaires, une seule instance, reprise après échec. Une tâche existante attribuée à un autre déploiement est refusée.

L'installation crée aussi `Codex-Voice-Calibration-Docker-Logon`, qui exécute uniquement `docker desktop start` à l'ouverture de session, sous le jeton interactif du même utilisateur et avec privilèges ordinaires. Elle ne stocke aucun mot de passe et ne lance aucun travail métier. Docker Desktop nécessite donc une session utilisateur ouverte sur ce poste ; le démarrage avant connexion n'est pas validé. Une tâche Docker existante avec une identité ou une commande différente est refusée.

La tâche appelle `boot_watchdog.py`, qui prépare les runtimes déclarés et conserve les logs dans `watchdog.log`. `watchdog.ready` contient le PID et l'identité du boot Windows pour distinguer un vrai reboot d'un simple redémarrage de processus. Les timeouts/erreurs du lanceur de récupération maintiennent le watchdog en attente bloquée. Le watchdog ne démarre pas Docker Desktop lui-même : si le daemon est indisponible, la santé est indisponible et le propriétaire vivant n'est pas supprimé.
